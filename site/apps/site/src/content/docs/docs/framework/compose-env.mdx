Two conventions do most of the work in `docker/`: **one compose file per
service, plus a dev override**, and **three env layers under
`docker/.config/`**. Together they are why `make dev s=api` can start a subset
without a per-project runbook.

## Compose layering

<ComposeLayering />

Every service gets two files. `docker/compose/<service>.yml` is the baseline,
describing the service as it ships. `docker/compose/<service>.dev.yml` is the
override, describing what it needs while you are working on it.

```bash
make dev            # baseline + .dev.yml override, merged
make dev s=api      # just this service's files
make up             # baseline alone — the same file that ships
```

`make dev` brings the existing services down first, so it doubles as "restart
into a known state".

A typical dev override adds four things and nothing else:

```yaml
services:
  api:
    build:
      target: development        # the dev stage of the same dockerfile
    environment:
      - RUST_LOG=debug
    volumes:
      - ../../apps/api:/app      # source mount for hot reload
    healthcheck:
      disable: true              # or a relaxed one with room to boot
  db:
    ports:
      - "5432:5432"              # backing services get real host ports for GUI tools
```

Note what is *not* there: the application service publishes no HTTP host port in
either file. That is the [router's](/docs/framework/router/) job. Backing
services are the exception: a dev override exposes Postgres and Redis on their
conventional ports so `psql` and Redis GUIs work.

### Composition, not duplication

Compose's `include:` is how a service pulls in the backing services it needs
without owning them:

```yaml
include:
  - path: ./db.yml
  - path: ./redis.yml
    optional: true
```

Two services that both need Postgres include the same `db.yml`. One database,
declared once. Marking an include `optional: true` lets a service degrade to
running without it.

## The three env layers

All under `docker/.config/`:

| File | Holds | Committed |
|---|---|---|
| `.env.shared` | values every service needs: project name, ports, shared hostnames | yes |
| `.env.secrets` | credentials, API keys, database passwords | **no** (gitignored) |
| `.env.<service>` | one service's settings | yes |

`.env.secrets.template` *is* committed, with the keys and no values. `make init`
copies it to `.env.secrets` if that file does not exist, which is why `make init`
is in the quickstart and is safe to re-run. `make doctor` warns when the secrets
file is missing. Generate values with `make make-key BYTES=32 FORMAT=hex`.

### Precedence, precisely

Compose applies `env_file` entries in order and **later entries win**. Then the
`environment:` block wins over all of them, and a value already exported in your
shell wins over the compose file's interpolation defaults.

The order the shipped recipes emit is:

```yaml
env_file:
  - ../.config/.env.secrets
  - ../.config/.env.shared
  - ../.config/.env.<service>
```

so for an application service the effective precedence is
`environment:` → `.env.<service>` → `.env.shared` → `.env.secrets`.

:::caution[The backing-service compose files list them the other way round]
`db.yml` and `redis.yml` order theirs `.env.shared` → `.env.secrets` →
`.env.<service>`, which puts secrets *above* shared for those two services. In
practice it rarely bites, because the same key is seldom defined in both files.
But if you are debugging a value that will not take, check which order the
compose file you are looking at actually uses. Do not assume; read the
`env_file` block.
:::

### A worked example

This site's own compose file (`site/docker/compose/site.yml`) is a plain
instance of all of it:

```yaml
services:
  site:
    build:
      context: ../../apps/site
      dockerfile: ../../docker/dockerfiles/site/app
      target: runner
    env_file:
      - ../.config/.env.secrets
      - ../.config/.env.shared
      - ../.config/.env.site
    environment:
      - NODE_ENV=production
      - PORT=4321
      - DATABASE_URL=postgres://${DB_USER}:${DB_PASSWORD}@db:5432/${DB_NAME}
    networks:
      - default
      - devmesh-traefik
```

`DB_USER` and `DB_PASSWORD` are interpolated by Compose from the environment at
`docker compose` time. They come from the env files, and the composed
`DATABASE_URL` is then pushed into the container. The dev override supplies
`${DB_USER:-site}`-style defaults so a fresh clone starts without a populated
secrets file.

## Dockerfiles

`docker/dockerfiles/<service>/app` is the development image and `app.prod` the
shipped one. Both are usually multi-stage, and the compose files select a stage
with `build.target`. That is how one dockerfile serves `make dev` and
`make build s=api prod=1`.
